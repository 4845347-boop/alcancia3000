Alcancía 3000 · Arquitectura y análisis del código suministrado

INDEL · 3.º Desarrollo de Software B · 21 de octubre de 2026

1. Identificación y alcance

Archivo auditado: alcancia3000.html. Aplicación web de una sola página escrita en HTML5, CSS y JavaScript moderno (sin dependencias externas visibles ni backend). Uso individual, moneda USD. La interfaz está diseñada con ancho máximo de 480 px y puede abrirse desde una laptop.

La versión suministrada NO implementa SQL, SQLite, PostgreSQL, servidor, usuario/contraseña, roles ni IA externa. El requisito general del docente sobre base de datos relacional o IA debe evaluarse como pendiente o por acordar, no como cumplido.

2. Arquitectura real

Presentación: HTML/CSS con navegación y vistas generadas desde funciones JavaScript. Reglas de negocio: validación de montos, sumas, porcentajes de metas, rachas, desbloqueo de logros. Persistencia: objeto global db serializado como JSON mediante localStorage.setItem('alcancia3000.v1', JSON.stringify(db)).

El navegador carga db desde localStorage; si no encuentra datos compatibles, crea categorías y logros iniciales con seed(). Se usa valid() para comprobar la estructura general del respaldo.

Flujo

Usuario → Evento de pantalla → Validación → Modificación del objeto db → save() en localStorage → render() → Vista actualizada.

3. Estructura de información y relaciones

No hay tablas físicas ni claves foráneas SQL. Las siguientes son colecciones JSON en db, y las relaciones por identificador son lógicas:

ColecciónCampos presentes en el códigoRelación
categoriasid, nombre, tipo1:N con movimientos mediante categoria_id
movimientosid, tipo, monto, fecha, descripcion, categoria_idN:1 con categorias
metasid, nombre, monto_objetivo, monto_actual, fecha_creacionNo guarda historial de aportes en colección separada
retosid, descripcion, condicion, monto_meta, fecha_inicio, estado1:N con rachas mediante reto_id (normalmente una racha por reto)
rachasid, reto_id, dias_consecutivos, mejor_racha, ultima_fechaN:1 lógica con retos
logrosid, nombre, condicion, fecha_desbloqueoSin relación obligatoria con otras colecciones
configid, moneda, preferenciasObjeto único

Los montos monetarios se guardan como centavos enteros. El diagrama adjunto presenta este modelo lógico, no un esquema de tablas SQL desplegadas.

4. Reglas de negocio y cálculos

ProcesoImplementación
Ingresos, gastos y saldototals(): saldo = suma de ingresos − suma de gastos.
Validación monetariaparseMonto(): números positivos con hasta dos decimales, convertidos a centavos.
Progreso de metapct(meta): porcentaje de monto_actual / monto_objetivo, limitado visualmente a 100%.
Abono de metaopenAbono(): suma el abono directamente en monto_actual, sin crear registro en movimientos.
RachasretoHoy() evita doble marcación del mismo reto en el mismo día.
LogroscheckLogros() verifica condiciones definidas y almacena fecha_desbloqueo.
Exportación/importaciónJSON descargable mediante Blob; FileReader para importar, con validación general y confirmación.

5. Instalación y ejecución

  1. Copiar el archivo alcancia3000.html a la laptop.
  2. Abrirlo con Chrome o Edge.
  3. Registrar al menos un movimiento y cerrar/reabrir para probar persistencia.
  4. No instalar paquetes ni ejecutar comandos, ya que el HTML incorpora estilos y lógica JavaScript.

Ubicación de almacenamiento: asociada al origen/perfil del navegador; no es un archivo de base de datos SQLite visible en la carpeta del proyecto. Su comportamiento con archivos file:// puede variar entre navegadores.

6. Seguridad y limitaciones conocidas

  • Datos solo en el navegador y sin autenticación; personas con acceso al perfil podrían consultar la información.
  • La función esc() codifica texto insertado en HTML para reducir riesgos de inyección en vistas.
  • El importador comprueba estructura general, pero no valida rigurosamente cada dato interno.
  • No hay auditoría, sincronización, cifrado de datos en reposo ni permisos por rol.
  • Los abonos a metas no disminuyen automáticamente el saldo disponible.
  • Las rachas de reto se basan en pulsaciones manuales; no confirman el cumplimiento material del ahorro.
  • Gráficas y cálculos son locales y no constituyen IA generativa.

8. Mejoras pendientes

Si el docente exige una BD relacional, se requiere desarrollar una capa de datos real (por ejemplo, SQLite con una aplicación anfitriona o un backend local). Si exige IA, también debe implementarse una integración específica y documentar claves y funcionamiento. Ninguna de esas funciones debe darse por desarrollada en el HTML actual.
